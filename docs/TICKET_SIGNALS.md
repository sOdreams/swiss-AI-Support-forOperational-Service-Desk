# Current signals, known checks and evidence coverage

This extension makes six data patterns visible to Filter, Resolve and the analyst:
process boundaries, preceding changes, business impact/scope/time, known or missing
prerequisites, historical verification and coverage of the selected evidence.
All UI text and generated explanations are English; original quotes are preserved.

## Call and module boundaries

```text
Ticket → Clean ──────────────────────────────────────────┐
       → FAISS Top-50 → Filter + cited current signals ──┴→ Resolve → Review
```

Filter extracts signals in its existing model call. Clean still runs in parallel.
Resolve uses those interpretations with the original facts; it does not assume
they are independently verified. The full cold workflow still makes three model
calls: Clean, Filter and Resolve. Warm analysis needs one Resolve call, and a
cached complete result needs none. Reasoning remains disabled, output is capped
at 1,500 tokens per call, and no retry was added. Extra schema/input/output text can
increase latency despite the unchanged call count.

No FAISS artifact rebuild or query rewrite is needed. Original Top-50 ranks and
scores are retained. Routing can consume cited observations through the analysis
contract without entering the retrieval query. [Priority calculation and advisory
routing](TRIAGE_HANDOFF.md) are implemented separately; automatic assignment is not.

## Filter output

`POST /tickets/analyze`, `POST /tickets/resolve` and the Python stage/composition
methods include two new fields under `filter`:

```typescript
signals: {
  observations: Array<{
    kind: "last_known_good" | "first_observed_failure" | "change_event"
      | "blocked_outcome" | "scope" | "workaround" | "deadline" | "constraint";
    text: string;
    evidence_ids: string[];
    evidence: Array<{ fact_id: string; source: string; text: string }>;
  }>;
  prerequisites: Array<{
    check: string;
    state: "satisfied" | "missing" | "contradicted";
    evidence_ids: string[];
    evidence: Array<{ fact_id: string; source: string; text: string }>;
  }>;
}
evidence_support: {
  state: "procedure_reference" | "analogue_only" | "no_selected_evidence"
    | "unavailable" | "needs_review";
  reason: string;
  active_comment_count: number;
}
```

There are at most eight observations, one per kind, and three prerequisite checks.
Unknown/not-applicable observations are omitted; omission does not mean false.
Every item needs one or two current Q IDs. The server attaches literal quotations;
the model writes only short interpretations (220 characters per observation,
180 per check). Unknown IDs, empty citations, duplicate kinds/checks and blank
text fail validation without retry. Unavailable filtering returns empty signals;
retrieval failure can still give `filter=null` as before.

`last_known_good` describes a reported successful earlier step, while
`first_observed_failure` describes the failed/missing output. Neither proves root
cause. A preceding broker change is a lead, not proof of a broken mapping. Relative
deadlines remain as written; they are not converted using the server's current date.
Reported impact/workaround can inform a later priority module; random historical
Priority/Urgency/Impact labels are not used for voting.

For a `satisfied` prerequisite, the cited current text must explicitly establish
the detail. A requested approval is not granted approval, and granted approval is
not completed provisioning. A reported configuration change does not identify its
exact mapping or establish that someone inspected it. For a `missing` check, the
citations explain why the detail matters, not proof that the detail was refused.
Checks must be relevant to a current request or observation, not invented policy.
Citation membership is validated; semantic correctness still needs analyst review.

## Coverage semantics

| State | Meaning |
|---|---|
| `procedure_reference` | At least one active `reference`/`conditional` historical comment; prerequisites and current applicability still need checking. |
| `analogue_only` | Primary case narratives were selected, but no active historical procedure. Current-fact diagnostics may still help. |
| `no_selected_evidence` | No primary case or active procedure was selected from this candidate pool. This is not a claim that the entire knowledge base lacks an answer. |
| `unavailable` | Filtering was not successfully completed, so coverage is unknown. |
| `needs_review` | Service is unresolved or clean/filter interpretations conflict; historical procedures are on hold. |

Coverage is derived by the server from validated selections, not generated by the
LLM. Reconciliation recomputes it after moving conflicting selections to reserve.
The count is of distinct active comment IDs; repeated historical occurrences do
not count as independent successes or increase an answer-confidence score.

## Historical verification

The evidence adapter extracts the final clause starting with an explicit
verification verb such as `confirmed`, `validated`, `verified`, `verifying`,
`reconciled` or `spot-checked`. `verification_excerpt` is a literal substring of
the original comment, or null when no bounded clause is found. Results are cached
for up to 4,096 distinct comment texts; extraction uses no LLM or new index.

This lightweight lexical rule is intentionally incomplete. It can miss implicit
verification, and a matched clause may describe a failed or insufficient check.
The complete historical comment remains authoritative context. Resolve uses
relevant clauses to suggest *future* verification, not to assert current success.
The UI exposes them in each action's Source section as **Historical verification**.
An offline semantic resolution-card index remains a separate future experiment.

## Resolve and feedback

Resolve receives the compact signal packet with Q IDs. It should use the process
boundary to explain the next diagnostic step, acknowledge satisfied checks, and
ask a single missing decision-changing question. Source conditions are still
attached by the server. Model output is not guaranteed to satisfy these semantic
instructions merely because its JSON is valid.

`resolution.context_signals` preserves the usable observations/checklist with
quotes; `resolution.evidence_support` preserves the coverage assessment. The
existing proposal hash includes them, and existing resolution feedback saves them
with the original proposal. No database migration is needed. Older saved analyses
without signals remain usable by standalone Resolve, with empty signal lists.
Conflicting/unavailable filtering does not supply its signals to Resolve.

The frontend shows **Situation and known checks** between cleaning and resolution.
It distinguishes **Already established in the ticket**, **Not established** and
**Contradicted by current evidence**. Source quotations remain expandable. Analyst
Use / Edit / Not applicable decisions and actual outcomes are still separate;
no suggestion or historical verification automatically fills the actual outcome.

## Implementation and verification

- `analysis/contracts.py`: signal schema, validation and exact current quotations.
- `analysis/evidence.py`: cached literal verification extraction and coverage logic.
- `analysis/prompts.py`: extraction in the existing Filter call.
- `analysis/pipeline.py`: coverage after selection and conflict reconciliation.
- `analysis/resolution.py`: current signals, verification context and proposal snapshots.
- `frontend/src/features/analysis/TicketSignalsPanel.tsx`: observations/checklist/coverage UI.
- `backend/tests/test_signals.py` and `frontend/e2e/resolution.spec.ts`: citation rejection,
  no extra calls/query changes, conflict handling, source retention and review persistence.

All 56 backend tests and 15 browser tests pass, along with frontend type checking,
lint and production build. The [live smoke report](../backend/validation/ticket-signals-smoke.json)
records fresh Clean/FAISS/Filter/Resolve calls on six selected development cases.
These examples informed prompt changes. It is a functionality/latency check with
qualitative observations, not a held-out GT evaluation or proof of improvement.

All six cold workflows returned validated outputs and retained 50 candidates,
using 18 total model calls and zero reasoning tokens. The complete Python workflow
took **6.50–11.83 seconds**, with a median of **9.13 seconds**, excluding loading,
HTTP and rendering. This is not comparable to the earlier Resolve-only timing.
Known approval stayed satisfied in case 14; the exact changed mapping stayed
missing in case 18; explicit working/failing steps were separated in cases 6, 13,
18 and 19. Remaining semantic limitations are recorded per case in the report.
